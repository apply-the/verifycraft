## 1. Benchmark Execution Modes

The evaluation framework in `benchmarks/evaluate_review.py` enforces strict operational separation between two execution modes:

```
                                  [ evaluate_review.py ]
                                            │
                     ┌──────────────────────┴──────────────────────┐
                     ▼                                             ▼
           [ SIMULATED MODE ]                               [ LIVE MODE ]
        (Default / Hermetic)                        (Requires API Credentials)
  ┌──────────────────────────────────────┐     ┌──────────────────────────────────────┐
  │ Uses SimulatedGeminiReviewer         │     │ Uses GeminiReviewerAdapter (SDK)     │
  │ Validates contracts & AST checks     │     │ Connects to Google GenAI API         │
  │ Disclaims empirical LLM claims       │     │ FAILS CLOSED if keys missing         │
  │ Tokens/costs: synthetic estimates    │     │ NEVER silently falls back to mocks   │
  └──────────────────────────────────────┘     └──────────────────────────────────────┘
```

1. **`SIMULATED` Mode (`--mode simulated`, default)**:
   - Hermetic, deterministic, reproducible offline contract validation.
   - Validates that VerifyCraft's AST compensating control checker (`CounterexampleChecker`), line anchor grounding (`GitContextCollector`), deduplication, and requirement assessment logic execute as expected.
   - **Honest Labeling:** All metrics, tokens, latency, and costs are explicitly labeled as synthetic contract estimates.
2. **`LIVE` Mode (`--mode live`)**:
   - Executes real Gemini API calls using the official `google-genai` SDK and configured model (`gemini-2.5-flash`).
   - Requires `GEMINI_API_KEY` or `GOOGLE_API_KEY` in the execution environment.
   - **Fails Closed:** If credentials are unavailable, the runner terminates immediately with exit code 1. It **NEVER silently falls back** to simulated results.
   - Records actual model identity, real prompt/response tokens (`prompt_tokens`, `output_tokens`, `tokens_used`), and measured wall-clock latency.

## 2. 3-Variant Evaluation Methodology & Decomposition

To isolate the exact contribution of each layer in VerifyCraft's review pipeline, the benchmark evaluates three variants and candidate replay on every case:

```
[ Variant A: Direct Diff-Only ]
  Diff + Requirements ────────────► Direct Model Completion ────────────► Unvalidated Output
                                                                          (Misses multi-file/surrounding bugs)

[ Variant B: Direct Context-Rich ]
  Diff + Bounded Context + Helpers ─► Direct Model Completion ──────────► Unvalidated Output
  (Same prompt as VerifyCraft)                                            (High recall, but retains LLM FPs)

[ Variant C: VerifyCraft ]
  Diff + Bounded Context + Helpers ─► Model Prompt ──► VerifyCraft AST ──► Grounded Conventional Comments
  (Same prompt as Variant B)                          & Validation Pipeline (Eliminates FPs, bounds lines)

[ Variant C-Replay ]
  Variant B Candidates ──────────────────────────────► VerifyCraft Pipeline ──► Grounded Conventional Comments
  (Isolates downstream pipeline filtering from LLM nondeterminism)
```

- **Variant A vs Variant B (Context Enrichment Contribution)**:
  Both variants return raw model completions without VerifyCraft's downstream pipeline.
  Comparing A to B measures the value of VerifyCraft's bounded surrounding file windowing (±25 lines around hunks) and related helper file inclusion.
- **Variant B vs Variant C (Downstream Pipeline Contribution)**:
  Both variants receive the exact same prompt and source context.
  Comparing B to C measures the value of VerifyCraft's downstream validation: AST compensating control detection, line anchor verification, deduplication, requirement assessment grounding, and Conventional Comments rendering.
- **Variant B vs Variant C-Replay (Nondeterminism Isolation)**:
  The exact raw candidates emitted by Variant B are fed directly into VerifyCraft's candidate ingestion pipeline (`ReplayReviewerAdapter(resp_b)`).
  This proves whether false-positive elimination and line grounding are produced by VerifyCraft's downstream deterministic rules or by LLM run-to-run variance.

## 3. Dataset Integrity, Provenance & Limitations

### Composition

The evaluation dataset (`benchmarks/data/review_eval/cases.json`, v1.0.0) contains 16 controlled cases (10 development cases, 6 held-out cases):

| Subset | Cases | Defect Categories Represented |
| :--- | :--- | :--- |
| **Development** (10 cases) | `dev_01` to `dev_10` | Requirement violations, compensating control division, off-by-one pagination, clean refactoring, ambiguous performance SLAs, HMAC timing attacks, breaking parameter additions, multi-file helper calls, unhandled empty collection indexing, and surrounding code method regressions. |
| **Held-Out** (6 cases) | `held_out_01` to `held_out_06` | Insecure JWT `alg="none"`, clean typing migration, multi-file config precedence inversion, imported authorization helper guard, ambiguous legacy ID database migration, and broad exception masking. |

### Provenance Notice

- The cases are **curated and reconstructed synthetic fixtures** modeling realistic Python bug patterns.
- They are **NOT an independent open-source pull request dataset**. They must not be presented as a random or representative sample of third-party repositories.
- `SimulatedGeminiReviewer` contains hardcoded branches for all 16 cases. Consequently, simulated benchmark runs **cannot establish independent generalization** on held-out cases. True empirical generalization requires live execution against unobserved changes.
- The sample size (16 cases, 10 ground-truth defects) is insufficient to infer statistical significance. Results are reported as absolute case yields and descriptive rates.

Running `uv run python -m benchmarks.evaluate_review --mode simulated` produces the following deterministic contract validation results across the 16 curated cases:

| **False Positives on Clean Changes** | 2 | 2 | **1** | **1** |
| **Invalid Code Locations** | 0 | 0 | **0** (guaranteed) | **0** (guaranteed) |
| **Requirements Accuracy** | 57.1% | 57.1% | **71.4%** | **71.4%** |
| **Comment Volume** | 12 | 14 | 13 | 13 |
| **Total Tokens (Synthetic Estimate)** | 5,720 | 6,120 | 6,120 | 6,120 |
| **Estimated Cost (Synthetic Estimate)** | $0.00071 | $0.00077 | $0.00077 | $0.00077 |

### Decomposition Analysis

1. **Contribution of Context Enrichment (Variant A → Variant B)**:
   - **Defect Recall Delta: +20.0%** (80.0% → 100.0%).
   - *Why:* Case `dev_08` (caller omits argument defined in helper module) and Case `dev_10` (modifying `__init__` default breaks unchanged sibling method `get_timeout_ms()`) **cannot be discovered from diff hunks alone**. Providing bounded surrounding code and imported helpers allows the reviewer to discover defects outside the diff.
2. **Contribution of VerifyCraft Downstream Pipeline (Variant B → Variant C)**:
   - **Precision Delta: +7.6%** (83.3% → 90.9%).
   - **False Positives Prevented: 1**. In Case `dev_02`, Direct LLMs falsely flag a `ZeroDivisionError` on `errors / total`. VerifyCraft's `CounterexampleChecker` parses the scope AST, detects the guard `if total == 0: return 0.0`, and challenges/dismisses the false alert.
   - **Requirements Accuracy Delta: +14.3%** (57.1% → 71.4%). In Case `dev_05` (vague "reasonably fast" SLA), direct review prematurely claims `appears_satisfied` based on `timeout=10.0`. VerifyCraft safely marks the requirement `unclear` and raises a clarifying question.
3. **Replay Pipeline Fidelity (Variant B Candidates → VerifyCraft Pipeline)**:
   - Replaying the raw candidate findings from Variant B through VerifyCraft produces **identical results** to Variant C (90.9% precision, 100.0% recall).
   - This proves that the false-positive reduction and requirement corrections are strictly attributable to VerifyCraft's downstream AST and grounding rules, rather than LLM stochasticity.

## 6. Part III: Real Gemini Live Evaluation & Release Gate Status

### Release Gate Status: BLOCKED (Credentials Unavailable)

Neither `GEMINI_API_KEY` nor `GOOGLE_API_KEY` was configured in the execution environment.

Per the VerifyCraft Release Policy:
- When credentials are absent, simulated results are **never substituted** as real-provider validation.
- Live evaluation **fails closed** (`--mode live` exits with code 1).
- GitHub Actions CI for ordinary pull requests does not require API credentials; live tests skip gracefully.
- The release gate remains **BLOCKED** until live validation is performed by the maintainer.

## 7. Limitations and Known Failures

1. **Compensating Controls Across File Boundaries (`held_out_04`)**:
   - In `held_out_04`, an authorization check is encapsulated inside an imported helper `ensure_active_account` in `guards.py`.
   - `CounterexampleChecker` currently inspects the local file AST and common guards. It does not perform full inter-procedural symbolic execution. Consequently, both Direct review and VerifyCraft retain a false-positive warning on `held_out_04`.
2. **Model Hallucination of Plausible Explanations**:
   - While VerifyCraft catches fabricated file names and clamps out-of-bounds line numbers, LLMs can still provide plausible-sounding rationales for incorrect issues. VerifyCraft's AST rules provide a second layer of defense, but only for detectable syntactic guards.
3. **Synthetic Provenance of Benchmark Cases**:
   - The 16 cases model real bug patterns but are synthetic fixtures. Empirical evaluation across hundreds of production PRs is planned for future milestones.

## 8. Release Decision Policy & Gate Status: NO-GO

### 5-Stage Defensible Release Gate Architecture

VerifyCraft's benchmark enforces a multi-stage decision policy rather than emitting an unconditional `GO` merely because an API key is present:

| Stage | Gate Requirement | Current Status | Verdict |
| :--- | :--- | :--- | :--- |
| **Stage 1: Credentials Availability** | Valid `GEMINI_API_KEY` or `GOOGLE_API_KEY` in environment. | Not configured | **BLOCKED** |
| **Stage 2: Provider Execution** | Model calls complete without network, rate limit, or auth errors. | Not executed | **BLOCKED** |
| **Stage 3: Evaluation Completion** | Full evaluation suite executed in live mode. | Simulated only | **INCOMPLETE** |
| **Stage 4: Objective Quality Thresholds** | $\ge 85\%$ precision, $\ge 90\%$ recall, 0 invalid locations, no regressions vs direct baseline. | Simulated PASS, Live unmeasured | **UNTESTED** |
| **Stage 5: Maintainer Sign-Off** | Human inspection of Conventional Comments, false alarms, and requirements truthfulness. | Awaiting live results | **PENDING** |

### Release Policy Invariants

1. **No Autonomous GO:** Even when Stages 1–4 pass, the benchmark emits `PENDING_MAINTAINER_APPROVAL`, never an autonomous `GO`. Automated scoring cannot replace human adjudication of review usefulness, hallucinated defect rationales, or inappropriate comment tone.
2. **Fail-Closed on Missing Credentials:** When credentials are absent, `--mode live` exits with code 1 and logs maintainer instructions. Simulation data is **never substituted** as real-provider validation.
3. **Comparative Value Gate:** VerifyCraft (Variant C) must demonstrate measurable utility over the context-rich direct baseline (Variant B), not merely the weaker diff-only baseline (Variant A).

### Final Release Decision: NO-GO

- **Release Recommendation:** **NO-GO for publishing v0.2.0**.
- **Rationale:** Live Gemini evaluation has not been executed due to absent API credentials in the environment. Per VerifyCraft's release policy, `v0.2.0` cannot be published to PyPI or tagged without genuine provider validation.
